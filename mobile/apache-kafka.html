What is Apache Kafka?

Apache Kafka. A system that stores streams of events so several applications can read the same history. An event is a record of something that happened, such as a completed trade.

Suppose an exchange reports a completed trade and labels it T42. Kafka can keep that report available even after one application has read it.

T42 records one execution: 0.4 units traded at 10:03 UTC.
01 The event log02 / 70

What is a collector?

Collector. A program that receives data from an outside source. When the collector sends an event to Kafka, it acts as a producer. A program that reads that event from Kafka is a consumer.

Our collector receives T42 from the exchange and sends it to Kafka once. A fraud service reads it to check for unusual activity. An analytics application reads it to calculate trading volume.

Exchange → collector → Kafka → two independent consumers

What is a topic?

Topic. A named stream in Kafka to which producers write records and from which consumers read.

Give completed trades their own topic so a consumer can calculate volume from executed quantities. A quote only states a price someone is willing to trade at.

trades.raw → executed trades · quotes.raw → offered prices

Open the envelope

Record. One item stored in Kafka. Its value contains the data being sent. Its optional key identifies what the data belongs to.

The key can guide partitioning. The value carries the payload. Headers can carry tracing metadata. A schema documents how applications interpret the bytes.

Key BTCUSDT · value T42 and price · header trace-id
01 The event log05 / 70

Why keep a log?

Partition. One ordered sequence of records within a topic. Kafka adds new records to the end of that sequence, forming a log.

A partition is an ordered log. Reading a record leaves it available to other readers while retention allows. This makes it possible to rebuild a derived dataset.

Fraud reads today; tomorrow analytics rereads the same partition
01 The event log06 / 70

What does a broker do?

Broker. A Kafka server that stores records and serves requests. Several brokers working together form a cluster. A replica is a copy of a partition.

A cluster can spread partitions across machines. Each partition has a leader that handles writes. Other brokers can hold copies so the partition can survive a server failure.

Broker A leads partition 0; broker B leads partition 1
01 The event log07 / 70

Who coordinates metadata?

KRaft controller. A server role that manages information about the cluster, called metadata. Controllers use agreement by a majority, or quorum, to keep that information consistent.

In KRaft, a controller quorum maintains cluster metadata. The active controller coordinates changes such as partition leadership. Broker and controller are distinct roles.

Controller metadata describes where a partition lives; its records live on brokers

How do you locate T42?

Offset. A number identifying a record’s position in one partition. The same number can occur in another partition.

Record the topic, partition and offset together. If a collector sends T42 a second time as a new record, the business ID can stay the same while its Kafka coordinates change.

trades.raw / partition 2 / offset 105

Which clock is this?

Record timestamp. A time attached to a Kafka record. The event time is when the real-world occurrence took place.

The record timestamp can represent producer creation time or broker append time, depending on configuration. Keep the exchange’s business timestamp explicitly in the payload.

Execution 10:03 → collector receives 10:05 → broker appends 10:06

Can two readers disagree?

Consumer position. The next offset a reader will fetch in a partition. Different readers can reach different positions in the same retained history.

The fraud service and analytics application advance independently. To investigate a disputed total, compare their filters and the same completed input range.

Reveal the takeaway

Fraud reached offset 110; analytics reached 104. First compare both through 104.

Where does a key go?

Partitioner. The producer logic that selects a partition for a record. A keyed partitioner can use the bytes representing the key to choose its destination.

With a consistent keyed partitioner, identical serialized keys map to the same partition while the partition count stays fixed. This can keep a symbol’s updates together.

BTCUSDT → partition 2 on successive sends
02 Partitioning and scale12 / 70

What exactly is ordered?

Append order. The order in which Kafka adds records to a partition. A source sequence number instead records the order assigned by the originating system.

Offsets define append order inside one partition. Independent producers or late arrivals can append an older business event after a newer one. Carry a source sequence when business order matters.

Offset 106 may carry exchange sequence 99 after sequence 100
02 Partitioning and scale13 / 70

What if the key is empty?

Batch. A collection of records sent together. An unkeyed record carries no key for the producer to use when choosing its partition.

A producer may distribute unkeyed records to improve batching. With no entity key, records for one symbol can land on different partitions.

An unkeyed trade has no symbol-based placement guarantee
02 Partitioning and scale14 / 70

Why does one partition overheat?

Hot key. A key that appears so frequently that its partition receives a disproportionate share of the work.

A popular symbol can account for most traffic. Adding partitions alone does little when every record for that key follows the same route.

One symbol generates 80% of writes → inspect load per partition
02 Partitioning and scale15 / 70

Can you split a hot key?

Shard. One of several pieces of a workload. A shard suffix is an extra value added to a key to spread its records across more destinations.

Add a shard suffix if downstream logic tolerates separate ordering domains. Aggregating per symbol now requires combining partial results.

BTCUSDT:0 and BTCUSDT:1 → two partial volumes → sum
02 Partitioning and scale16 / 70

What changes when you add partitions?

Hash-based routing. A partition-selection rule that computes a number from the key and maps it to one of the available partitions.

Increasing the count can remap keys with hash-based routing. Existing records stay where they were written, so a key’s history may span partitions.

A consumer following only the new partition misses older T42 records
02 Partitioning and scale17 / 70

How much parallelism fits?

Consumer group. A named set of consumers that share reading work. An assignment tells each member which partitions it should read.

In a conventional consumer group, a partition is assigned to at most one member at a time. More consumers than partitions leaves some members idle.

6 partitions + 8 consumers → at most 6 actively assigned
02 Partitioning and scale18 / 70

Name your ordering boundary

Ordering boundary. The set of records whose order your application must preserve. It might be all changes for an account or all executions for a trading symbol.

Using account ID as the key preserves placement by account. Using symbol preserves placement by symbol. Decide which state updates must run sequentially.

Account balances → account key; per-symbol book → symbol key

Measure ingress first

Throughput. The amount of data processed per unit of time. Ingress measures incoming data, usually in records or bytes per second.

Multiply message rate by average serialized size to estimate incoming payload bandwidth. Replication, protocol overhead, compression and bursts change actual network use.

2,000 records/s × 500 bytes = 1 MB/s before overhead

Consumer lag. The distance between a group’s saved reading position and the end of a partition. Both positions in this example refer to the next offset.

The log end is the position after the newest record. The committed position is where the group will resume. Move it toward the end to see the gap shrink.

03 Producing reliably21 / 70

Who converts objects to bytes?

Serialization. Converting an in-memory value into bytes that Kafka can store. Deserialization reconstructs a usable value from those bytes.

A serializer turns your trade object into bytes. Consumers need a compatible deserializer and schema. Identical-looking keys encoded differently can route differently.

UTF-8 text “42” and a binary integer 42 are different keys
03 Producing reliably22 / 70

What did send confirm?

Acknowledgment. A response reporting the outcome of a write under the producer’s settings. An asynchronous call lets the application continue while waiting for that response.

An asynchronous send can return before Kafka acknowledges the write. Observe the returned future or callback. A full local buffer or serialization failure can also surface at the caller.

Accepted in client memory → sent → acknowledged or failed
03 Producing reliably23 / 70

Why batch sends?

Linger time. How long a producer may wait for more records to fill a batch before sending it. Latency is the time an operation takes.

Producers group records destined for the same partition. A short wait can create fuller batches and reduce request overhead, with a latency trade-off under light load.

Inspect batch.size and linger.ms together
03 Producing reliably24 / 70

Where does compression help?

Compression. Encoding a batch in fewer bytes so it takes less space to transmit or store.

Compressing batches can save network bandwidth and disk. The benefit depends on data redundancy, batch size and CPU budget. Benchmark with representative payloads.

Repeated JSON field names often compress well across a batch
03 Producing reliably25 / 70

Choose the acknowledgment level

Leader and followers. The leader is the replica that receives writes for a partition. Followers copy its records. Replicas keeping up within Kafka’s limits are called in sync.

acks=0 skips broker acknowledgment. With 1, the leader acknowledges locally. With all, the in-sync replicas must acknowledge under the applicable replication rules.

A successful leader-only acknowledgment can precede follower replication
03 Producing reliably26 / 70

Why can a timeout duplicate a trade?

Timeout. A limit on how long a sender waits for a response. Reaching the limit leaves the sender uncertain whether the write succeeded.

The broker may append a record even when its response never reaches the producer. The sender sees an unknown outcome and may retry.

Append T42 → response lost → resend T42
03 Producing reliably27 / 70

What idempotence covers

Idempotent production. A producer feature that prevents its own transmission retries from appending the same send more than once.

An idempotent producer lets the broker recognize retries of its own sends. Publishing T42 again as a new application send is still a separate operation.

Transport retry vs second business submission → different deduplication needs
03 Producing reliably28 / 70

When does a transaction help?

Transaction. A set of writes that Kafka commits or aborts as a unit. A committed-data reader excludes records from aborted transactions.

A producer transaction can group writes to several Kafka partitions. Consumers using read_committed see committed transactional data and skip aborted writes.

Write T42 to trades and audit → commit both together
03 Producing reliably29 / 70

Who fences a stale producer?

Producer fencing. Kafka’s mechanism for stopping an obsolete producer instance from continuing to write under a transactional identity taken over by its replacement.

A stable transactional.id identifies a logical producer across restarts. A newer instance using that identity can fence the stale one. Distinct live producer tasks need distinct identities.

Replacement for task 7 reuses its ID; task 8 uses its own
03 Producing reliably30 / 70

What if the send ultimately fails?

Source cursor. The producer application’s saved position in the system it reads. Advancing it tells the application which input to fetch next.

Choose an explicit recovery path. If you advance the source cursor after a failed send, the missing event may never reach Kafka. Retain enough input to retry.

Reveal the takeaway

Advance the source cursor only after the intended durability boundary succeeds.

04 Consuming and recovery31 / 70

Who owns the position?

Poll and commit. A poll fetches records for a consumer. A commit saves the group’s next reading position so a replacement consumer can resume.

A consumer polls assigned partitions and advances its local position. The group’s committed offset records where recovery should resume. These positions can differ during processing.

Polled through 105 → local next 106; committed next still 100
04 Consuming and recovery32 / 70

What number should you commit?

Completed range. A consecutive run of records whose required work has finished. The first unfinished record determines the safe recovery position.

Commit the next offset you intend to read after successful work. If 105 was the last finished record and all preceding work is complete, commit 106.

Processed offsets 100–105 → next offset 106
04 Consuming and recovery33 / 70

Crash after writing the sink

Sink. The destination where a consumer writes its result. At-least-once processing allows the same record to reach that destination again after a failure.

The sink accepts T42 but the consumer crashes before committing. Recovery rereads T42. A stable unique key can make the second sink write harmless.

Commit after durable write → possible repeat
04 Consuming and recovery34 / 70

Crash after committing first

At-most-once processing. A recovery policy in which a record may be skipped but the consumer does not retry it after recording progress.

Commit first and the restart can skip records whose sink writes never finished. This order may lose business effects even though Kafka retained the input.

Commit 106 → crash before writing 105 → restart at 106
04 Consuming and recovery35 / 70

What starts a rebalance?

Rebalance. A change in which consumer owns each partition in a group. Revocation means a consumer gives up an assignment.

Membership or partition changes can trigger reassignment. A worker losing partitions must stop work on them and handle outstanding writes consistently.

Consumer B joins → some assignments can move from A to B
04 Consuming and recovery36 / 70

Why did a healthy worker lose work?

Poll interval. The elapsed time between a consumer’s calls to fetch work. Kafka uses a configured maximum to detect members that stop polling.

A worker can remain alive while a processing loop takes too long between polls. Check max.poll.interval.ms and the amount of work returned per poll.

Slow database write → poll gap grows → assignment can move
04 Consuming and recovery37 / 70

Where does a new group start?

Offset reset. A rule for choosing a starting point when a group has no usable saved offset for a partition.

auto.offset.reset matters when a valid committed position is unavailable. Earliest starts at the oldest available data. Latest starts at the current end.

Changing reset policy alone does not rewind a healthy existing group
04 Consuming and recovery38 / 70

Can one group replay safely?

Backfill. Reading an earlier interval of input to create or repair historical results. A separate group can maintain its own progress during the run.

For an independent backfill, use a separate group and a controlled output. Replaying into the same append-only sink can duplicate a full period of results.

analytics-backfill reads history while analytics-live keeps running
04 Consuming and recovery39 / 70

How do you handle a poison record?

Poison record. An input that consistently fails processing, such as a value that cannot be decoded. Quarantine is durable storage for inspecting failed inputs later.

Isolate the original bytes, source coordinates and failure reason. Only advance past the record when its durable disposition matches the pipeline’s policy.

Malformed JSON → quarantine with topic, partition and offset
04 Consuming and recovery40 / 70

How quickly can lag clear?

Net drain rate. The speed at which accumulated work shrinks after subtracting newly arriving work from processing capacity.

Use the net drain rate. While 900 events/s arrive and the consumer handles 1,200/s, only 300/s reduce the existing backlog.

Reveal the takeaway

90,000 waiting ÷ 300 per second = 300 seconds, if rates remain stable.

What is replicated?

Replication factor. The number of copies Kafka maintains for each partition, counting its leader.

A partition leader handles writes and followers replicate its log. Replication factor counts copies, including the leader. It describes copy count, not the acknowledgment policy.

Replication factor 3 → one leader + two followers
05 Replication and retention42 / 70

What is the ISR?

In-sync replica set (ISR). The replicas Kafka currently considers sufficiently caught up with the partition leader.

The in-sync replica set tracks replicas sufficiently caught up under Kafka’s rules. A replica leaving the ISR reduces the set available for durable acknowledgments.

Replicas A/B/C exist; current ISR may contain only A/B
05 Replication and retention43 / 70

What does minimum ISR enforce?

Minimum ISR. The configured lower bound on in-sync replicas required for a write using all-replica acknowledgments.

With acks=all, min.insync.replicas can reject writes if too few replicas are in sync. It sets a floor; all current ISR members still participate under standard ISR semantics.

RF 3, min ISR 2, only 1 in sync → write rejected
05 Replication and retention44 / 70

Why spread copies across racks?

Failure domain. Infrastructure that can fail together, such as servers connected to the same power supply in one rack.

Replicas on hosts sharing one failure domain can fail together. Rack-aware placement helps distribute copies across physical or availability-zone boundaries.

A rack outage should leave replicas in another rack
05 Replication and retention45 / 70

How does deletion retention work?

Retention. The policy that determines how long or how much history Kafka keeps. A log segment is a file holding part of a partition’s history.

Kafka stores partitions in segments. Time or size retention can remove old eligible segments. A consumer falling behind retention may lose access to its required offsets.

A three-day outage needs more than one day of retained history
05 Replication and retention46 / 70

What does compaction retain?

Log compaction. Background cleanup that can discard older records for a key while retaining its latest value.

Compaction eventually removes superseded values for a key. Consumers may see multiple versions before cleaning. A compacted topic suits rebuilding current state.

Account A balance 10 → 15 → eventual latest value 15
05 Replication and retention47 / 70

What does a tombstone mean?

Tombstone. A keyed record with a null value that signals removal of that key in a compacted topic.

In a compacted topic, a keyed record with a null value signals deletion. Tombstones are themselves retained for a limited time. A long-offline replica may miss that signal.

Key A, null value → remove A from the materialized view
05 Replication and retention48 / 70

Are missing offsets corruption?

Offset gap. A range of positions with no readable record. Removing records during compaction leaves later offsets intact.

Compaction can remove a record without renumbering later offsets. A consumer starting in a gap can advance to the next available record.

Offsets 100 and 103 can be adjacent retained records
05 Replication and retention49 / 70

Budget disk realistically

Storage footprint. The space consumed by retained data and its replicas. Headroom is spare capacity reserved for growth and operations.

Start with payload bytes per second, retention duration and replica count. Adjust for compression, segment overhead and free space needed to operate.

1 MB/s × 86,400 s × 3 replicas ≈ 259.2 GB per day uncompressed
05 Replication and retention50 / 70

Replication or backup?

Backup. An independently recoverable copy of data. A replica is a live copy that follows changes to its source.

Replicas can faithfully copy a bad producer write. Recovery from accidental deletion or corrupted business data may require independent history and a tested rebuild procedure.

Reveal the takeaway

If every replica contains the same bad correction, replay a trustworthy source.

What does Kafka Connect do?

Kafka Connect. A framework for moving data between Kafka and external systems. A connector is the component that understands a particular source or destination.

Connect runs connectors that move records between Kafka and external systems. A source connector writes Kafka records. A sink connector reads them.

Database changes → source connector → Kafka → storage sink

How do connector tasks scale?

Connect worker and task. A worker is a running process that hosts connector work. A task executes one share of that work.

A connector can divide work into tasks. The connector implementation and source partitioning constrain parallelism. Raising the task limit does not guarantee more useful workers.

One indivisible source shard can remain a bottleneck

What does CDC publish?

Change data capture (CDC). Publishing database changes as events. A primary key identifies the affected row, and an operation field says what changed.

Change data capture represents inserts, updates and deletes from a source. Preserve primary key, operation and source ordering metadata so downstream consumers can rebuild state.

Trade T42 · correction · source sequence 11

Snapshot before change stream

Snapshot. A baseline view of a source at a known point. A change log records subsequent changes so a reader can advance from that baseline.

A snapshot supplies a baseline. A consistent handoff to the change log prevents missing or double-applying changes around the boundary. Follow the connector’s source-specific protocol.

Snapshot state at position L → consume changes after L

Why use an outbox?

Transactional outbox. A database table that stores events awaiting publication alongside the business operation that produced them.

A service can write its business change and an outbox row in one database transaction. A publisher relays that row to Kafka. Repeated relay attempts still need event identity.

Order committed with event E7 → relay E7 → consumer deduplicates

Who owns a schema?

Schema registry. A service that stores and versions data-format definitions. Producers and consumers can refer to the same definition when encoding or decoding a record.

Agree on field names, types, nullability and units with the teams producing and consuming the topic. A schema registry can help enforce compatibility when used with compatible tooling.

price in cents → decimal reais is a semantic change

Which reader must survive?

Backward compatibility. The ability of a newer reader to interpret data written with an older schema.

Backward compatibility means a new reader can read older data under the chosen format’s rules. Test retained historical messages as well as current producer output.

Replay yesterday’s schema through today’s deserializer
06 Integration and contracts58 / 70

Which state belongs in Streams?

Kafka Streams. A library for building applications that transform Kafka records. A state store keeps information the application needs across records.

Kafka Streams applications can maintain keyed local state and recover it from changelog topics where enabled. Repartitioning may be needed before grouping by a different key.

Trades keyed by trade ID → rekey by symbol → aggregate
06 Integration and contracts59 / 70

Where does exactly-once end?

Atomic commit. One decision that makes a set of changes take effect together. In a Kafka transaction, those changes can include output records and consumed offsets.

A transactional consume-transform-produce workflow can atomically commit Kafka output and consumed offsets. An external email, HTTP call or database update needs its own consistency mechanism.

Kafka transaction commits → independent HTTP charge still needs idempotency
06 Integration and contracts60 / 70

When is Kafka enough?

Stream processing. Applying logic as records arrive, such as joining a trade with reference data or calculating a volume-weighted average price (VWAP).

Persist immutable trades in a retained log for replay and decoupling. Add a processing engine when you need windows, joins, enrichment or durable derived tables.

Reveal the takeaway

Kafka retains input; a Spark query can turn that input into five-minute VWAP.

Identify the principal

Principal. The identity under which a client connects. Authentication verifies that identity.

Authentication establishes which identity is connecting. Use a distinct principal per workload so access and audit events map back to an owner.

Collector and analytics reader use separate credentials

Authorize the operation

Access control list (ACL). Rules specifying which identities can perform which operations on which resources. Checking those permissions is authorization.

An ACL can scope a principal to operations on resources such as topics and groups. Check both topic-read and group permissions when a consumer cannot start.

A reader may access trades.raw yet lack access to analytics-live

Encrypt the connection

Transport Layer Security (TLS). A protocol that encrypts a connection and can verify the server’s identity using a certificate.

Configure TLS on client and broker listeners and validate the broker’s identity. Authentication and authorization remain separate decisions.

A trusted certificate secures transport; a topic ACL controls access

Group coordinator. The broker responsible for coordinating a consumer group. A group description reports reading progress by partition.

Describe the group and compare partition-level offsets. One partition far behind while others are current points toward skew, a slow worker or a stuck key.

kafka-consumer-groups.sh --bootstrap-server HOST:9092 --describe --group analytics-live

Which latency matters?

End-to-end latency. The elapsed time from a business event occurring to its processed result becoming available.

Broker round-trip time measures only one leg. Capture business time, ingest time and sink visibility time to explain user-facing delays.

Trade 10:03:00; visible 10:03:08 → 8 s end-to-end

Can the sink keep up?

Bottleneck. The step that limits overall processing speed. Backpressure occurs when slow downstream work constrains upstream progress.

An overloaded database can slow a healthy Kafka consumer. Compare incoming rate, processing time and sink write latency before adding brokers.

Producer rate steady + sink time rising + lag rising → inspect sink

Reconcile the handoff

Lineage. Information connecting a result to the records and processing steps that produced it. Reconciliation compares records or totals at an agreed boundary.

Keep source coordinates for lineage and a business ID for semantic deduplication. Record counts can differ legitimately when a correction updates an existing entity.

Two offsets for T42 → two log records, one current silver row

Practice a controlled replay

Controlled replay. Reading a known set of retained records again with a defined start, destination and expected result.

Produce three synthetic trades to a test topic. Read them with one group, then a fresh group starting earliest. Compare keys, partition and offset across the two reads.

Expected: both groups can observe the same retained coordinates

Design the recovery story

Recovery boundary. The point from which work resumes after a failure. To explain a retry, distinguish an event’s identity, its stored location and its business version.

Your collector can resend, a sink can time out and the consumer can restart. Which three identifiers explain what happened to T42? Reveal the answer before opening the Spark deck.
