What is Structured Streaming?

Apache Spark Structured Streaming. A processing engine that runs a query repeatedly as new data arrives. A stream is a sequence of incoming records, such as trades reported by an exchange.

Suppose a trading exchange reports a trade named T42. Give Spark a rule to add each trade’s quantity to a five-minute total. As more trades arrive, Spark updates the relevant total.

Trade T42: 3 units at 10:03 → add 3 to the 10:00–10:05 total

What is a streaming DataFrame?

DataFrame. A table-like collection of rows with named columns. A streaming DataFrame represents rows that can continue arriving after a query starts.

Define columns for trade ID, execution time, symbol and quantity. A DataFrame expression can group those rows by symbol. Spark applies the expression as input arrives.

T42 and T43 are rows. Quantity is a column. Total quantity is a result.

How does Spark process incoming rows?

Micro-batch. A bounded slice of incoming data that Spark processes as one unit. Spark assigns each slice a batch ID within the query’s checkpoint history.

Spark can process several trades together. If T42 and T43 arrive in time for the same batch, one execution of the query handles both.

Batch 12 reads T42 and T43. Batch 13 picks up the next available trades.

Who runs a micro-batch?

Driver, executors and tasks. The driver coordinates a Spark application. Executors are the processes that perform the work. A task is one unit of work an executor runs.

The driver schedules tasks for a batch. Executors can parse different portions of the input at the same time. The batch must wait for its required tasks to finish.

One task parses T42; another parses T43.

What is incremental here?

State. Information the query remembers between inputs. A stateless operation handles each row independently. A stateful operation also uses previously retained information.

A row filter can evaluate each new row independently. A running count must remember earlier contributions. Identical DataFrame syntax can hide very different state and resource requirements.

price > 0 → local decision; count by symbol → prior state

Source, plan and sink

Source and sink. A source supplies input rows. A sink receives query results. A query plan describes the operations Spark performs between them.

Trace a single trade across those three pieces. Check what Spark read, what the rule calculated, and what the destination actually stored.

Source: incoming trades → plan: sum quantities → sink: table of totals

What starts a query?

Streaming query. A running computation that reads new input, applies a transformation and sends results to a sink.

A streaming DataFrame describes the computation. Configure its writer and call start to launch it. Use the returned query object to inspect progress or stop the run.

query = writer.start()

Processing-time triggers

Trigger. A rule that tells Spark when to start processing available input. Processing time is measured by the execution clock.

A processing-time trigger requests a cadence for micro-batches. If a batch takes longer than the interval, the next one cannot finish on the original schedule.

10 s requested, 17 s processing → the query falls behind its cadence

Process available data and stop

AvailableNow. A trigger that processes the data available at the start of a run and then stops. A checkpoint saves durable recovery information between runs.

AvailableNow is useful for scheduled incremental processing on supported sources. It processes the input available for that run, potentially in several batches, then terminates.

Run nightly from the same checkpoint to process the next available data

Which mode is this guide using?

Execution mode. The strategy Spark uses to process incoming data. In micro-batch mode, foreachBatch can run a user-defined function on each batch of output rows.

Use micro-batch mode for the Kafka-to-Delta example. Other execution modes have different operator and sink support. Check the guide matching your installed Spark distribution before adopting a low-latency mode.

Connect to a Kafka topic

Kafka connector. The integration that lets Spark read from or write to Kafka. A Kafka topic is a named stream of records. A subscription selects which topics to read.

Set the Kafka source, bootstrap addresses and a subscription. Use the connector artifact compatible with your Spark and Scala build. The example assumes a configured session named spark.

raw = (spark.readStream.format("kafka").option("kafka.bootstrap.servers", brokers).option("subscribe", "trades.raw").load())

Read the envelope first

Kafka record coordinates. A partition is one ordered part of a Kafka topic. An offset identifies a position in that partition. Together with the topic, they locate a stored record.

Kafka source rows expose key and value as binary fields plus topic, partition, offset and timestamp. Keep these coordinates when extracting the business payload.

T42 at trades.raw partition 2 offset 105 → recover its exact input row

Decode using a contract

Schema. A description of field names, types and structure. A decoder interprets stored bytes so Spark can extract those fields.

For JSON encoded as UTF-8, cast the value to string and parse it with an explicit schema. Avro and other binary encodings need their corresponding decoder.

from pyspark.sql import functions as F parsed = raw.withColumn("trade", F.from_json(F.col("value").cast("string"), schema))

Do malformed events disappear?

Malformed record. A record whose contents cannot be interpreted under the expected format. A Kafka tombstone is a keyed record with an intentionally null value.

Parsing can yield null fields. Separate malformed payloads, missing mandatory fields and genuine Kafka tombstones before aggregating. Save raw bytes and failure context for investigation.

Non-null bytes + missing trade ID → quarantine with source offset
02 Read and validate15 / 70

Which timestamp drives the metric?

Event time. When the business event happened. Ingestion time is when a receiving system took it in. Processing time is when the query worked on it.

An exchange records execution at 10:03. Kafka receives it at 10:05. Spark reads it at 10:06. For a trading-volume chart, assign the event to its execution-time window.

10:03 belongs to [10:00, 10:05) even when processed later
02 Read and validate16 / 70

Normalize time units

Epoch timestamp. A count of time units since a defined reference instant, commonly midnight UTC on 1 January 1970. The unit is part of its meaning.

A numeric timestamp needs a declared unit. Parsing microseconds as milliseconds can create invalid dates or extreme future times. Check plausible bounds before computing watermarks.

A thousandfold unit mismatch can push the watermark far ahead
02 Read and validate17 / 70

Preserve price precision

Decimal precision and scale. Precision is the maximum total number of digits in a decimal value. Scale is the number of digits to the right of the decimal point.

Choose types that can hold the largest expected price, quantity and product. A volume-weighted average price uses the sum of price times quantity divided by total quantity.

Quote value = trade price × base quantity

Choose initial Kafka offsets

Starting offset. The position where a new Kafka reader begins within a partition. A resumed Spark query uses its saved source progress.

startingOffsets controls a fresh query. A resumed query reads its checkpoints. Use a separate checkpoint for a deliberate replay and ensure the required offsets still exist.

.option("startingOffsets", "earliest")
02 Read and validate19 / 70

Can files be a streaming source?

File source. A streaming input that discovers newly available files. Atomic publication makes a complete file visible in one step.

A file source discovers files over time. Publish complete files atomically where supported and use stable names. Mutating an already-processed file is an unreliable correction mechanism.

Publish trades-001.parquet once; deliver corrections as new input

Archive the evidence

Bronze and Silver. Bronze is a raw storage layer that preserves what arrived. Silver is a derived layer where the pipeline validates and normalizes those records.

Keep original bytes and source coordinates in Bronze. If a parser used the wrong quantity type, Silver can be rebuilt from the retained inputs even after Kafka removes them.

Reveal the takeaway

Keep raw bytes, source coordinates and ingest time alongside parsed columns.

03 Time and state21 / 70

A five-minute tumbling window

Tumbling window. A fixed interval that groups events by timestamp. Consecutive intervals meet at their boundaries and do not overlap.

Each event belongs to one non-overlapping interval. Spark windows use a half-open boundary. A trade executed exactly at the end starts the next window.

10:04:59 → [10:00,10:05); 10:05:00 → [10:05,10:10)
03 Time and state22 / 70

A sliding window overlaps

Sliding window. A fixed-length interval that starts repeatedly at a chosen step. When the step is shorter than the length, one event can belong to several windows.

With ten-minute windows starting every five minutes, the same trade contributes to two windows. Summing overlapping window totals double-counts their shared events.

10:07 belongs to [10:00,10:10) and [10:05,10:15)
03 Time and state23 / 70

A session window follows activity

Session window. A group of events for one key separated by no more than a configured inactivity gap. The group grows as qualifying activity arrives.

A session groups nearby activity for the same key. A gap can end the current session. A late event may bridge intervals that previously appeared separate.

Gap 5 min: events at 10:00 and 10:03 can belong together
03 Time and state24 / 70

What does the watermark track?

Watermark. An event-time progress threshold Spark uses to decide when certain state can be finalized or removed. The delay threshold allows for out-of-order arrivals.

For one input, Spark derives a watermark from observed event-time progress and a delay threshold. It can lag the simple subtraction across triggers. It does not advance merely because the wall clock ticks.

Max observed 10:20 − delay 10 min → candidate 10:10
03 Time and state25 / 70

Explore the lateness allowance

Lateness allowance. The duration subtracted from observed event-time progress when calculating a candidate watermark for one input.

Fix the maximum observed event time at 10:30. Move the allowed delay to see the candidate watermark. Allowing more lateness can keep more state and delay final output.

10 min
Max event time 10:30 · Candidate watermark
03 Time and state26 / 70

How late is too late?

Late data. A record whose event time trails the progress already observed by the query. State eviction means discarding information for an older group or window.

For supported event-time aggregations, the delay gives a one-sided guarantee. Data less late than the threshold is protected under the documented conditions. Older data may still be processed or may be dropped.

Never model the threshold as a promise that every older row is dropped
03 Time and state27 / 70

Apply the watermark to the right column

Event-time column. The timestamp field used to assign each row to a window. Watermark metadata associates the allowed delay with that field.

Define it before the aggregation, on the same event-time column used for windowing. The aggregation and output mode must allow state cleanup.

timed = trades.withWatermark("event_ts", "10 minutes")
03 Time and state28 / 70

How many keys stay in memory?

Cardinality. The number of distinct keys or groups. Every active combination of grouping key and time window can require a separate state entry.

State grows with active key-window combinations. A million symbols or sessions can require far more state than a small fixed key set, even with the same input row rate.

1,000 symbols × 6 open windows → up to 6,000 aggregate keys
03 Time and state29 / 70

What if one stream goes quiet?

Global watermark. The event-time threshold a multi-input query uses to coordinate state handling across its input streams.

For multi-input stateful queries, the default global watermark policy follows the slowest input watermark. A faster policy can advance sooner and drop records from a slower stream.

Trades advance; confirmations pause → final output may wait
03 Time and state30 / 70

Where does state live?

State store. Spark’s component for reading, updating and recovering intermediate state. A provider implements how those entries are stored.

Spark’s state store maintains intermediate keyed data across micro-batches and persists recovery information through the checkpoint. A state-store provider such as RocksDB can change memory and disk behavior.

Reveal the takeaway

Inspect state metrics before choosing a provider or shortening the lateness window.

04 Aggregates and joins31 / 70

Build volume by symbol

Windowed aggregation. A calculation over records sharing a grouping key and time interval. Trade volume is the sum of executed quantities in the group.

Group by the time window and symbol, then sum validated trade quantities. Spark maintains one running total per active key-window pair.

volume = timed.groupBy(F.window("event_ts","5 minutes"), "symbol").agg(F.sum("qty").alias("volume"))
04 Aggregates and joins32 / 70

Calculate VWAP correctly

Volume-weighted average price (VWAP). The average execution price weighted by the number of units traded. A three-unit trade contributes three times the weight of a one-unit trade.

Accumulate traded value and quantity separately. Divide only after summing. An unweighted average gives a tiny trade the same influence as a large one.

1 unit at 100 and 3 at 104 → (100 + 312) ÷ 4 = 103
04 Aggregates and joins33 / 70

Which trade opened the window?

Tie-breaker. An extra ordering field used when two events have the same timestamp. A shuffle moves records between tasks and can change their arrival order.

Arrival order can differ from execution order. To derive open and close, select by a deterministic business ordering, including a tie-breaker. Plain first and last after a shuffle can be unstable.

Sort criterion: (event time, exchange sequence) for each symbol/window
04 Aggregates and joins34 / 70

Append mode

Append output mode. A policy that emits newly added result rows once Spark can publish them as final for the supported query.

Append publishes rows the query considers final. For a supported watermarked window aggregation, output waits until the watermark passes the window end. An unaggregated input row may be appendable immediately.

Window ends 10:05; final row arrives after sufficient event-time progress
04 Aggregates and joins35 / 70

Update mode

Update output mode. A policy that emits result rows changed during a trigger. An upsert inserts a missing key or updates its existing row.

Update mode emits result rows changed since the previous trigger. The downstream system must understand repeated updates to the same key. Supported combinations depend on the query and sink.

Volume 4.0 then 4.7 → replace the same window total
04 Aggregates and joins36 / 70

Complete mode

Complete output mode. A policy that publishes every row of the current result table each time the query produces output.

Complete mode outputs the entire result table on each trigger for supported aggregations. The cost grows with the table, and old aggregate state is retained for full reporting.

100,000 groups → a new full result even when few groups changed
04 Aggregates and joins37 / 70

Enrich with a reference table

Stream-static join. A match between incoming rows and a reference dataset read as a batch table, using a shared key such as symbol.

A supported stream-static join can attach a symbol’s quote currency or venue. Decide which reference version belongs to each trade if historical classifications change.

T42 + symbol reference → BTCUSDT, quote currency USDT
04 Aggregates and joins38 / 70

Match two live streams

Stream-stream join. A match between rows arriving on two streams. Each side may need to remember records while waiting for a counterpart.

To match trades to confirmations, join on a business key and define a meaningful time range. Watermarks and a suitable time predicate allow Spark to retire state that can no longer match.

Same trade ID; confirmation time between execution and execution + 15 min
04 Aggregates and joins39 / 70

Why did the unmatched row arrive late?

Outer join. A join that can preserve a row even when it has no match, filling the missing side with null values.

A supported outer stream-stream join must wait until watermark progress and its time condition make a future match impossible under the policy. Idle input can delay null-extended results.

No confirmation yet → wait → publish unmatched trade when eligible

Which duplicates can you drop?

Deduplication. Recognizing repeated copies of the same logical event and keeping one. A corrected version is a new business fact when the source defines it that way.

On supported Spark versions, dropDuplicatesWithinWatermark can deduplicate by business ID while using an event-time watermark. Set the delay for the expected timestamp spread of duplicates. A legitimate correction needs its own version identity.

Reveal the takeaway

T42 version 1 twice is a retry. T42 version 2 can be a correction.

05 Delivery and recovery41 / 70

What’s inside a checkpoint?

Checkpoint location. A durable directory where Spark records information needed to resume one streaming query, including progress and any recoverable operator state.

A query checkpoint records recovery information such as source progress, commit information and state for stateful operators. Use durable storage and a dedicated location per query.

Silver trades and Gold volume each own a checkpoint directory
05 Delivery and recovery42 / 70

Who owns Kafka progress?

Source progress. A record of how far a query has read in each input. For Kafka, a batch covers a range beginning at its start offset and ending before its end offset.

The Spark Kafka source recovers progress from the query checkpoint. Looking only at Kafka consumer-group commits can misrepresent what this query processed.

Spark progress for partition 2 ends at 106 → compare to the source’s available end
05 Delivery and recovery43 / 70

When does a batch repeat?

Side effect. A change outside Spark’s internal computation, such as writing to a database. Retrying a batch can repeat that change.

A failure after an external write and before Spark records completion can cause the same input batch to execute again. Repeated processing must yield the intended sink state.

Batch 12 writes T42 → crash → batch 12 runs again
05 Delivery and recovery44 / 70

What exactly is exactly once?

Exactly-once result. A result equivalent to applying each intended input once, including after recovery. A replay-safe sink can accept repeated work without duplicating its effect.

A recoverable source and checkpoint support deterministic replay. End-to-end guarantees also require the sink to handle repeats correctly. Spark’s Kafka sink, for example, documents at-least-once writes.

Exactly one business result requires reasoning about both ends
05 Delivery and recovery45 / 70

Use foreachBatch deliberately

Batch callback. A function Spark invokes with the output rows of a micro-batch and that batch’s ID. In PySpark, foreachBatch registers this function.

The callback receives a batch DataFrame and batch ID. It can call batch-only writers or MERGE logic. The callback may be invoked again for the same batch after a failure.

writer = trades.writeStream.foreachBatch(write_batch).option("checkpointLocation", checkpoint)
05 Delivery and recovery46 / 70

Can a batch ledger prevent repeats?

Batch ledger. A durable record of which batches a destination has successfully applied. Atomicity means data changes and their success record take effect together.

An external ledger helps only if marking success and applying the data are atomic or the writes are independently idempotent. Scope the batch ID by query lineage because a fresh checkpoint can restart numbering.

Write data + commit ledger in one transaction where supported
05 Delivery and recovery47 / 70

Can the checkpoint survive a code change?

State schema. The types and structure of the values a stateful operator saves. A restarted operator must be able to interpret its saved state.

Changing filters can differ from changing state keys or state schemas. Check the documented compatibility rules for the specific operator and runtime before restarting from an existing checkpoint.

New grouping key → plan a versioned query and rebuild if required
05 Delivery and recovery48 / 70

What if Kafka expired the offsets?

Retention gap. A range of input the query still needs but its source has already removed. The earliest retained offset marks the oldest readable position.

If the checkpoint needs data Kafka has discarded, replay from that source is incomplete. Identify the missing interval and recover it from an archive if available. Suppressing a data-loss error cannot reconstruct the rows.

Checkpoint expects 105; earliest retained 160 → investigate [105,160)
05 Delivery and recovery49 / 70

Why isolate a backfill?

Backfill. Reprocessing earlier data to create or repair results. A staging target holds those results separately while they are checked.

A separate checkpoint and staging target let you compare historical results without racing the live writer. Define the handoff offsets and business-time coverage before promoting results.

Replay through a known input boundary → reconcile → switch consumers
05 Delivery and recovery50 / 70

Test the failure boundary

Fault injection. Deliberately causing a failure in a test run to observe recovery. An idempotent write produces the same intended outcome when repeated.

Inject a test failure after writing a synthetic batch, then restart from its checkpoint. Compare business keys and totals against a clean run through the same offsets.

Reveal the takeaway

A successful retry restores the intended result and leaves no duplicated trade value.

What does a Delta commit describe?

Delta Lake. A table storage system that records changes in a transaction log. A successful transaction creates a new table version.

Delta Lake commits describe table versions. A table version is a storage-level ordering boundary. Multiple business records in a commit can share that version, so it may not uniquely order changes within a key.

Trade sequence 11 and 12 may be written in one table commit
06 Delta changes to Silver52 / 70

Why read a change feed?

Change data feed (CDF). A Delta feature that exposes row-level inserts, updates and deletes so downstream queries can follow changes.

A change data feed exposes row-level change events for supported tables and versions. On Databricks, confirm the table’s CDF mode and retained history before selecting a starting version.

An ordinary append stream and a change feed answer different questions
06 Delta changes to Silver53 / 70

Read the Delta change rows

Initial snapshot. The set of rows present in a table when a fresh feed begins. These baseline rows let a downstream reader build an initial state.

Read from the Delta source with readChangeFeed enabled. On a fresh stream without a starting version, the initial table snapshot is generally emitted as inserts before subsequent changes.

changes = spark.readStream.option("readChangeFeed", "true").table("bronze.trades")
06 Delta changes to Silver54 / 70

Preimage or postimage?

Preimage and postimage. The preimage is a row’s value before an update. The postimage is its value after that same update.

A Delta update can emit the row before and after the update. A current-state Silver table usually consumes the postimage for the new value; the preimage is useful for audit or reversing old contributions.

T42 qty 3 → 2: preimage 3, postimage 2
06 Delta changes to Silver55 / 70

Physical delete or business flag?

Physical delete and business delete. A physical delete removes a table row. A business delete can instead leave a row in place with a field indicating that the entity was deleted.

A physical Delta deletion appears as a delete change. A source application might instead write a row with op=D. These are separate signals. Explicitly map each to your Silver deletion contract.

_change_type=delete OR accepted after-image with op=D → delete intent
06 Delta changes to Silver56 / 70

Keep the metadata through Bronze

Control column. A field that tells the downstream pipeline how to interpret or apply a record, such as an operation code or a source-assigned sequence number.

Retain operation, source sequence and business key through parsing and renaming. If the pipeline drops a delete indicator before MERGE, a removed trade can remain active in Silver.

T42, source_seq 13, op D → preserve all three through staging
06 Delta changes to Silver57 / 70

Resolve competing changes for a key

Full after-image. A complete representation of a row after a change. A partial update supplies only changed fields and may depend on earlier updates.

A batch may contain several changes for one trade. For a current-state target and full after-images, choose the latest valid change using authoritative order. Partial updates may require applying every patch in order.

Sequence 11: qty 2; sequence 12: qty 1 → current qty 1
06 Delta changes to Silver58 / 70

Apply a replay-safe merge

Merge. An operation that matches incoming records to target rows by key, then inserts, updates or deletes according to rules. A version guard checks which change is newer.

For current state, update only with a newer source version, insert a valid new key, and apply a delete only when the version allows it. Define what happens when a delete arrives first.

Repeated T42 version 12 → a second merge should leave Silver identical
06 Delta changes to Silver59 / 70

Prevent deleted keys from returning

Deletion marker. A retained record that a key was deleted at a particular version. It helps distinguish an old replay from a genuinely new change.

Physically deleting a target row can erase the version you need to reject stale inserts. Keep a durable deletion marker or version ledger when out-of-order replay is possible.

T42 deleted at 13 → replay insert at 11 → reject using stored version 13

Why is Gold still wrong?

Gold and retraction. Gold holds business-facing results derived from Silver. A retraction reverses the contribution of an earlier input to a published result.

Updating Silver does not reverse a volume already emitted to Gold. Recompute affected windows from authoritative Silver or apply explicit signed corrections with deduplication.

T42 qty drops from 3 to 2 → a prior total of 10 becomes 9, assuming no other changes.

Read query progress

Query progress report. A summary of one completed trigger, including input counts, timing and available state metrics.

Inspect lastProgress for input rows, source offsets, trigger durations and state metrics. Record the query and run identifiers when comparing restarts.

print(query.lastProgress)
07 Production and practice62 / 70

Is the query catching up?

Processing rate. How many records the query completes per unit of time. Backlog is input that has arrived but has yet to be processed.

Compare offset growth at the source with completed query progress over wall-clock time. Spark’s reported processing rate alone can look healthy even as a skewed partition falls behind.

Incoming 2,000/s; sustained completed 1,500/s → backlog grows 500/s
07 Production and practice63 / 70

Limit intake deliberately

Intake limit. A bound on how much source input the query plans to process in a trigger. It controls batch size rather than guaranteeing an output rate.

maxOffsetsPerTrigger bounds how many Kafka offsets Spark plans per trigger, shared across topic partitions. Smaller batches can reduce peak pressure while increasing time to clear accumulated input.

.option("maxOffsetsPerTrigger", 50000)
07 Production and practice64 / 70

Find the slow stage

Stage. A set of tasks Spark can execute together as part of a job. The slowest part might also be outside a Spark stage, such as a destination write.

Separate time spent fetching offsets, executing tasks, committing state and writing the sink. An overloaded target can dominate trigger time while Spark executors appear underused.

15 s trigger; 12 s in external writes → investigate sink latency first
07 Production and practice65 / 70

Inspect skew after the shuffle

Data skew. An uneven distribution of work across tasks. A shuffle redistributes rows, often to bring the same grouping keys together.

Many balanced Kafka partitions can still feed one oversized aggregate key. Inspect task duration and partition sizes after repartitioning. Partial aggregation can help decomposable measures.

VWAP decomposes into sum(price × qty) and sum(qty)
07 Production and practice66 / 70

Watch the cost of state

State metrics. Measurements of the intermediate data the query keeps, such as the number of retained keys. An eviction policy governs when old entries can be discarded.

Track rows retained, rows updated and state-store metrics together with event-time progress. Growing state plus a flat watermark can indicate stalled input time or missing cleanup conditions.

Late-time allowance, key count and join range all affect retained state
07 Production and practice67 / 70

Reconcile at the same boundary

Reconciliation boundary. The input range or table version two results must share for a meaningful comparison. A superseded version has been replaced by a newer one.

Compare Bronze, Silver and Gold through the same offset range or Delta version. Distinguish filtered records, duplicates and corrections from missing rows.

6 raw rows − 1 retry − 1 superseded version = 4 current trades in this example

Practice with the rate source

Rate source. A built-in Spark source that generates synthetic timestamped numbers at a configured rate. The console sink prints query output for inspection.

In a Spark session, start a synthetic source in micro-batch mode. The console prints rows with timestamp and value. Stop the query when you finish observing the batches.

q = (spark.readStream.format("rate").option("rowsPerSecond", 2).load().writeStream.format("console").start())

Predict the window output

Expected result. A value calculated independently from known input. It gives a streaming test a concrete outcome to verify.

Feed two synthetic trades for one symbol into the 10:00–10:05 window. Quantities are 1 and 3; prices are 100 and 104. Predict volume and VWAP before testing a correction.

Volume 4, VWAP 103. Correct the second quantity to 2: volume 3, VWAP 308/3 ≈ 102.67.

Trace one missing delete

Root cause. The earliest defect that explains an observed error. A pipeline boundary is a handoff where you can check whether a change still has its intended meaning.

Bronze contains T42’s delete but Silver still shows the trade. Locate the feed version, inspect the decoded change and its source sequence, then verify the merge branch and target version. Reconcile the affected Gold window after fixing Silver.

Prove the first boundary where T42’s delete disappears or is rejected. Replaying earlier stages blindly can reproduce the same defect.
